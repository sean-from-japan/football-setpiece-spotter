# SoccerTrack v2 を実際に触って分かったこと

ここに書いてあることは、データセットカードの記述ではなく、配布されたファイルに対して実測したものです。両者が食い違う場合はカードの記述を引用し、違いを静かに直すのではなく見えるようにしてあります。

2026-09-06 に、試合118577の後半に対して確認しました。

## ダウンロード

**`hf download` は正常終了しながら0バイトのファイルを置いていくことがあります。** 状態注釈20本のうち15本と、映像の最初の1回で発生しました。コマンドは終了コード0を返し、保存先のパスを表示します。何も届いていないことはファイルサイズにしか現れません。Xetトランスポートを無効にすると解消します。

```bash
HF_HUB_DISABLE_XET=1 hf download atomscott/soccertrack-v2 --repo-type dataset \
  --include "videos/118577/118577_panorama_2nd_half.mp4" --local-dir data/soccertrack-v2
```

ダウンロードのたびにサイズを確認し、再試行の前に空のファイルを消してください。0バイトのファイルがすでに置かれていると、取得済みとみなされて飛ばされます。

## ファイルの中身

| | |
|---|---|
| 映像 | 4096 x 1080、H.264、25 fps、48:19、72,475フレーム、1ハーフ3.3 GB |
| 状態注釈 | ハーフごとにJSON 1本、2.5〜2.7 GB、整形済み |
| その中の選手座標 | 1ハーフで1,599,683行。バイト数にしておよそ1% |

状態注釈ファイルの大半は、全フレームぶん繰り返されたピッチのライン注釈です。`setpiece import-gsr` はこれをストリーミングで読み、選手座標を4.4 MBのgzip圧縮CSVとして2分以内に書き出します。

**注釈と映像はフレームサイズが違います。** 注釈上の画像は 3840 x 1504 で、配布される映像は 4096 x 1080 です。したがってピクセル座標（`bbox_image`）は、変換なしには映像へ重ねられません。ピッチ座標（`bbox_pitch`、単位はメートル）はこの影響を受けず、このプロジェクトが使っているのはそちらです。

`info` ブロックは定型文です。`game_id` が "7"、`id` が "1"、`game_time_start` が "1 - 00:00"、`clip_stop` が 30000 という値が、後半のファイルも含めてすべてのファイルで同一です。実際の値が入っているのは `seq_length` だけです。

## 時刻の対応

注釈は72,751フレーム、映像は72,475フレームで、差は276フレーム、およそ11秒です。454秒の地点でフレームを切り出して目視で確認しました。注釈では左のペナルティエリアに16人がいてコーナーフラッグの位置に選手が1人立っており、映像でも同じゴール前に同じ密集があり、反対側は空です。両者は数秒以内で揃っており、これは評価器が使う許容幅の内側です。

`bas/` の事象の時刻は、ハーフの開始からではなく**試合の開始からの通算**です。118577の後半は `position` 2,699,520 ms から始まります。映像上の時刻と比べる前に、後半の最初の値を引いてください。

## ボール軌跡は再開の検出には使えません

`ball/` はフレームごとの位置を与えますが、試合117092では次のようになっています。

- `status == 1`（追跡できている）が67,374フレーム中21,444フレーム、つまり**32%**です。
- 123件の `OUT` 事象のうち、**110件は直前4秒間に追跡できたボール位置がありません**。したがって大半の停止について、ボールがどこで外に出たかは不明です。
- 追跡できていないフレームは**ピッチ矩形にクランプされます**。その結果ボールはちょうど (52.5, -34.0)、つまりコーナーフラッグの位置に置かれます。「コーナー付近のボール」を探すとこれらのフレームが返り、この試合では5件、いずれもきれいな検出に見える誤検出です。

カードには試合132831と132877についてクランプの記載があります。117092でも同じことが起きています。

`setpiece corners` が選手座標だけを使っているのは、これが理由です。

## `raw/` には商用のイベントフィードが丸ごと入っています

`<match>_player_nodes.csv` はノードの一覧ではありません。401トークンの語彙を持つ試合イベントフィードで、1事象1行、`event_time`・`event_period`・チーム・正規化された位置・関与した選手を持ちます。

ボールアクションの注釈には無いセットプレーのラベルが入っています。

| トークン | 118577での件数 |
|---|---|
| `throwIn` | 44 |
| `freeKick` | 16 |
| `goalKickFailed` / `goalKickSucceeded` | 14 / 7 |
| **`cornerKick`** | **11**（前半6、後半5） |

これがコーナーの教師データで、選手追跡データとは独立しています。だからこそ、選手の配置に基づいて作った検出器を正直に採点できます。`setpiece` の `corner_labels()` がこれを読みます。

`event_time` は `bas/` と同じく試合開始からの通算です。このフィードは `SECOND_HALF` の開始を 2,700,000 ms とし、`bas/` は 2,699,520 ms としています。480 msの差は採点に使う許容幅の十分内側ですが、同一リリース内の2つのファイルの間にある本当の食い違いです。

## 同梱の較正データは、期待どおりに投影しません

`raw/` には `homography.npy`（3x3）、`mapx.npy`（1080, 4096, 2、int16）、`mapy.npy`（1080, 4096、uint16）が入っており、マップの形状は配布される映像とちょうど一致します。ところがホモグラフィのほうは、中心原点でも角原点でも、ピッチのメートルを映像のピクセルに写しません。1フレームの22人全員が幅150ピクセルほどの帯に投影されますし、付属のマップで `cv2.remap` を実行すると、歪みの取れた画像ではなく縦に潰れた画像が出ます。

リリースが説明していない手順がもう1つ挟まっているようです。それが分かるまで、このプロジェクトはピッチ座標を直接使い、映像への描画は行いません。教師データをフレームに重ねて表示するには、この点の解決が必要です。
